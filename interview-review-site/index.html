00 · The Pipeline — Who Owns What

先记住归属，再谈模块。

verl 拥有训练平面（Ray、FSDP2、优化器、权重同步、vLLM 引擎与调度）；我们拥有证据/认证平面（token 账本、verifier、逐 episode 认证、批级门禁）。接入点全是官方扩展点。

verl 拥有 · training plane

框架一行不替代

  • 训练循环：RayPPOTrainer.fit() 驱动每一步
  • 数学：GRPO advantage + PPO-clip + FSDP2 + 优化器
  • 引擎：vLLM colocated TP=2，显存与请求调度
  • 同步：update_weights 原地同步 + checkpoint（smoke27 实测 2.90/2.83s）
我们拥有 · evidence plane

框架给不了的证据

  • token 账本：逐轮原生 ids + logprobs，prompt 即账本
  • verifier：episode 内真实执行判分，PASSED/FAILED → 1/0
  • 认证：逐 episode + 批级门禁，fail-closed
  • loop 本体：PiAgentLoop 起真实 Pi 0.84.2（bwrap 隔离）

01 · Data Generation

从任务行到可信
token 序列。

数据生成分三层：任务侧（一行 = 一个 GRPO 组）、采样侧（每样本一次真实 Pi episode）、token 层（账本 + 原生桥 + 组装）。三层共同保证：进入清洗环节的每条样本，都是「策略在某一确定权重下真实生成」的完整证据。

Why base=pass only

平批死锁规则

方差门禁会把全对/全错批重采样重画；p≈0 或 p≈1 的任务会耗尽 max_attempts，该 step 永远过不去（resume 还重放同一任务）。

Band 分带 · P0 贪心

247 / 54 / 76 / 1

evalplus 状态分带：pass/pass 247、pass/fail 54、fail/fail 76、fail/pass 1。只从 base=pass 带等距取题。

Measured

15–65% 成功率带

r2 实测该带在自家 agent loop 下的解出率落在中段——正是 GRPO「有时对有时错」的理想区间。r3：60 题 × 5 epochs = 300 步。

1.2 采样侧 · src/integrations/verl/pi_loop.py — 每个样本一次真实 episode

PiAgentLoop(AgentLoopBase).run 是框架逐样本调用的入口。它不自己生成 token——它起一个真实的 Pi agent 子进程，让 Pi 通过我们的代理去打 verl 的 vLLM 引擎，全程留下证据。

STEP 0101

解析身份并命名 episode

读 manager 盖的章：pi_attempt（重采样轮次）、pi_sample_token（n 份复制除 uid 外无法区分）、pi_episode_root。目录 = call_root/attempt-N/{run_id}-{slug}-{token}（pi_loop.py:220-231）。

STEP 0202

建工作区（attempt 目录之外）

两个约束都踩过坑：orchestrator 对 episode 根 mkdir(exist_ok=False)，预建会团灭；批门禁把 attempt 下每个子目录当 episode，工作区混入会被读成「缺证据」（pi_loop.py:87-106）。

STEP 0303

起 Pi 子进程（bwrap 隔离）

Pi ⇄ 我们的代理 ⇄ vLLM。Pi 永不直接碰引擎——只有代理把每轮原生 ids+logprobs 记成身份绑定证据。工具集冻结 read/bash/write/edit/ls，schema 哈希逐请求校验（native_transport.py:192）。

STEP 0404

episode 内跑 verifier

Pi 结束后立刻跑 verify_mbpp_src.py（抽 assert、跑 solution.py），产出 verifier_status ∈ {PASSED, FAILED}（pi_loop.py:442-448）。这是逐 episode 第一道清洗，也是 reward 唯一来源。

STEP 0505

reward 映射与硬边界

PASSED→1.0，FAILED→0.0；其余一律 raise——基础设施失败不是合法的 0 奖励，绝不许把「没跑成」伪装成「做错了」（pi_loop.py:293-304）。

STEP 0606

落盘 admitted-sequence.json

prompt/response ids、mask、logprobs、reward、组号、双 checksum 全落盘；批门禁稍后从落盘证据重新认证，不信任内存对象（pi_loop.py:324-326）。

Ledger guards

账本的防线

既有消息全文比对；新 assistant 回合只比承重字段（tool_calls 必须一致，content 空不判改写——实测 Pi 回 content: null）；模板边界 after.startswith(before)；终止符被 vLLM 吞掉时下一轮以 mask=0 纯上下文补回。

Why lossless

为什么能「无损」接上 verl

verl 的 _agent_loop_postprocess 对返回的 AgentLoopOutput 从不重新 tokenize：response_ids 原样右填充，完全信任 response_mask（1=LLM 生成，0=观察）与 response_logprobs。这与 AssembledSequence 的语义逐字段同构——这就是整个接入设计的支点。

History rewrite

改写即拒绝

任何历史改写（压缩/截断/分支/回滚）→ history_rewritten=True → 拒绝整个 episode，绝不重 tokenize 收尾消息来圆（sequence.py:210-213）。

Placeholder

0.0 是「非概率」

观察位 logprob 用 0.0 显式占位——不是概率值；所有统计必须经 mask 排除（sequence.py:30）。占位让数组天然对齐，mask 让损失天然正确。

02 · Data Cleaning

认证不过，一步也不进训练器。

清洗不是后处理脚本，而是嵌在 generate_sequences 与训练器之间的门禁。契约是批级的（单一行为策略、episode 唯一、组规模、任务绑定、组内方差），而框架的 AgentLoopBase.run 是逐样本的——所以认证放在比 loop 高一层、比 trainer 低一层的 manager 上，且失败必须 fail-closed。

manager 从不算 advantage、不碰权重、不训练；它只做三件事：把当前轮策略注入批次、更新前验证整批、留下可审计的 lineage 记录。

为什么规则⑤是独立的 DegenerateBatchError

GRPO 的 advantage 是组相对散度：A_i = (r_i − mean(r_group)) / std(r_group)。全同奖励的组减均值后恒为 0，对优化器是纯噪声。拒绝这样的批是正确的；终止整个 run 是错的——什么都没被消耗，诚实的动作是重画一批。

所以「无方差」被编码成独立异常类型，成为重采样策略唯一的批级触发器。实测 Mbpp/118 解出率约 1/16，n=8 时平批概率不低——重采样是常规路径，不是异常路径（r3 甚至把 max_attempts 设到 20）。

prompts.non_tensor_batch["pi_policy_fingerprint"] = ...      # 指纹盖进批次，随批下行
prompts.non_tensor_batch["pi_expected_engine_step"] = ...    # 传输层逐调用校验引擎侧一致性

两个著名的坑 · 面试讲这两个最加分
「tuple != list，门禁永远不可能通过。」smoke24 · 定位难点：两边都持久化，事后无法复现差异
ProducerArtifact.from_dict 会对 payload 深度冻结：存证是 tuple，重建是 list，直接比较容器恒 False——smoke24 上四数组逐元素完全一致，批照样被拒。修复一：training_sequence_matches 逐元素比较，容器类型不参与判定；修复二：describe_sequence_difference 输出每字段长度 + 首个差异下标，「token 相同、容器不同」被如实报成比较 bug 而不是数据问题——修复前那条报错不指 episode 不指字段，代价是一整轮 GPU 猜谜。证据：sequence.py:98-164 · commit 6ec0ad5。元教训：比较语义要绑定数据的序列化语义。
「在自己 except 里 re-raise 的重试 = 单发。」smoke26 · 静默失败：不崩溃、无栈，只是让 max_attempts 失效
旧版 attempt 循环在 except 分支直接再抛——看起来像重试循环，行为是单发：一个零方差批直接终结整个 run。修复：重采样策略抽成独立纯函数 certify_with_resampling（不 import Ray/verl，CPU 可单测），白名单重试 + 拒绝落盘（commit bc06a5f）。沉淀的原则：让值得测的决策住在值得测的地方——它是框架侧管理器里唯一能脱离 GPU 验证的部分。证据：resampling.py:8-15 注释原话 “looks like a retry loop and behaves like a single shot” · smoke26 → smoke27 同配置对照。
03 · Expect These Questions

面试官会深挖的 16 个问题。

按真实面试节奏组织：设计动机 → 技术选型与对比 → 踩坑与优化 → 异常与边界。每题先给「一句话先答」，再展开；证据都标了出处。先自测，再展开对照。

A设计动机
verl 自带 tool_agent_loop，为什么要自己写一个 AgentLoop？追问：自写的边界在哪，哪些坚决不碰？
一句话先答：框架的 loop 能跑多轮工具调用，但给不了我们需要的证据平面——逐调用原生 token ids/logprobs、身份绑定、episode 内 verifier 与认证序列；我们换的是 loop 的「策略」，不是 loop 的「机器」。
  • 证据需求：训练要的不是 chat 文本，是「策略在某确定权重下逐 token 的真实生成」。Pi 只能经我们的代理访问引擎，token 走 AsyncLLMServerManager.generate(prompt_ids=…) 的 token RPC。
  • mask 语义：多轮要区分「模型生成的」与「喂回的观察」，response_mask 是我们的语义——正好利用 _agent_loop_postprocess 不重 tokenize 的事实。
  • 奖励语义：reward 必须来自 episode 内自己的 verifier（1/0），verl 的 reward manager 被绕过——这一点要如实说（实测 reward timing 4.77e-05s，是空转）。
  • 边界：训练循环、advantage、PPO-clip、FSDP2、优化器、权重同步、checkpoint、vLLM 引擎——一行不替代（smoke27 实测 update_actor 186.8/188.1s、update_weights 2.90/2.83s）。
证据：四个官方扩展点（§00 表）；pi_loop.py:1-22 模块注释。
可能追问：「为什么不往 verl 提 PR？」——证据捕获、fail-closed 认证是数据平面的私货不是通用需求；挂扩展点上升级框架零成本。
认证/清洗为什么放在 manager 层，而不是每个样本的 loop 里？追问：放在 trainer 侧不行吗？
一句话先答：我们的契约是批级的（单一行为策略、episode 唯一、组规模、任务绑定、组内方差），而 AgentLoopBase.run 是逐样本的——组语义只有凑齐整批才判得了。
  • 放在 manager（generate_sequences 内、返回前），认证落在「生成之后、trainer 消费之前」，失败无法被旁路：raise 让这次生成调用直接失败，trainer 拿不到批。
  • 放 trainer 侧（reward/advantage 阶段）太晚：批已进训练数据管线，拒绝意味着 trainer 代码也要改——而我们对训练器零侵入。
  • manager 只做三件事：注入当前轮策略、认证整批、留 lineage 记录。
证据：verl_manager.py:12-25（模块注释就是标准答案）；manager.py:77-132。
GRPO 下零方差批为什么必须丢弃？丢弃后为什么是「重画」而不是「跳过这一步」？追问：能不能给个小的默认 advantage？
一句话先答：GRPO 的 advantage 是组相对散度，全同奖励的组减均值后恒为 0，这批数据对优化器是无信号噪声；重画是因为什么都没被消耗，且这是抽签性质的问题——下一批可能有信号。
  • 不能造信号：给默认 advantage 等于把「没有证据的梯度」注入更新，与 fail-closed 哲学直接冲突。
  • 重画成本 = 一次 rollout；拒绝成本 = 一个 step。实测解出率约 1/16，重采样是常规路径——r3 把 max_attempts 设到 20。
  • 重画必须可审计：attempt 号预盖进批次、rejected-attempt{N}.json 落盘，防止重画的批伪装成一次过。
证据：resampling.py:1-15 模块注释；r3 筛题规则（base=pass 带 15–65%）正是为了让重采样保持低频。
可能追问：「max_attempts 耗尽怎么办？」——终止 run 报最后一次错误；resume 重放同一任务再暴露一次，逼你换数据。
为什么要做「prompt 即账本」的 append-only 设计？追问：严格契约是什么，为什么最后不需要松弛它？
一句话先答：多轮对话若每轮从 messages 重新渲染 prompt，历史里的模型 token 就会被重新 tokenize 改写——训练信号不再对应真实生成。账本让 prompt_{i+1} = prompt_i + gen_i + obs_i 由构造成立，原定严格契约无需任何松弛。
  • 只有两种编码发生：首轮冻结 prompt、每轮新观察后缀；已生成 token 永远逐字进账本。
  • 防御：既有消息全文比对；新 assistant 回合比承重字段（tool_calls 必须一致、content 空不判改写——实测 Pi 回 content: null）；模板边界 after.startswith(before)。
  • 终止符问题：vLLM 不返还特殊 stop token，<|im_end|> 缺席分不清「结束」与「截断」——账本记 terminator_stripped，下轮把终止符作为纯上下文补回（mask=0、无 logprob、永不进 loss）。
证据：token_context.py:1-11、:112-157；实测 smoke16 真实消息通过守卫且仅追加 20 个后缀 token。
B技术选型与对比
rollout 走 token 级 RPC 而不是 OpenAI chat API，为什么？追问：由此多出了哪些必须自己处理的问题？
一句话先答：chat API 只给文本，训练要的是每轮的原生 token ids 和 logprobs——这是行为策略证据（BEHAVIOR_LOGPROBS）的唯一来源，也绕开任何 decode/re-encode 漂移。
  • token RPC 直接拿 token_ids + log_probs，逐 token 校验（数量对齐、全部有限），缺失即 raise。
  • 代价是自己接管协议层：stop 控制（stop_token_ids=[im_end]）、预算（min(max_tokens, remaining)）、上下文拼接（账本）、工具解析、特殊 token 不返还的处理。
  • 采样参数显式进身份：sampling_fingerprint = sha256({temperature, top_p})，与策略指纹一起回答「这批样本是谁、在什么采样配置下生成」。
证据：native_transport.py:188-208；E 阶段数值证明：rollout 侧与训练侧重算 logprob Pearson 0.99957/0.99959。
工具调用解析为什么不能只信 vLLM 的 tool parser？「不修复」原则是什么？追问：parser 自己抛异常呢？
一句话先答：smoke16 实测 10/10 的生成里 hermes parser 解析出 0 个调用（模型输出裸 JSON 不带标签）——只信它就没有工具循环；同时解析器只做提取，绝不修复，坏输出交给奖励与批门禁裁决。
  • 三级策略：上游有结果 → 校验标签数与解析数一致（混合状态 raise，防半信半疑）；上游无结果但有标签 → 视为 malformed；全无 → 回落仓库唯一严格提取器 src.capture.tool_calls。
  • 不修复：未声明工具名 / 坏 JSON / 空 arguments → 产出空，无猜测。修复会制造「模型没说过的话」，污染行为策略证据。
  • 最新兜底：parser 自身抛异常（TypeError: unhashable type: 'dict' 实测出现过）→ 同样回落严格提取器——一个坏抽样不应报废整批。
证据：native_transport.py:16-50；token_context.py:16-32（工具参数 JSON 校验，坏参即 raise）。
数据集只有几十行时，「加数据」到底改变了什么？为什么筛掉 fail/fail 的题？追问：一行数据为什么不是意外？
一句话先答：train_batch_size=1 时行数 = 步数（1 行 × 5 epochs = 5 步，且是不同的题）；筛掉 fail/fail 是因为 p≈0 的题永远全错、必然平批死锁——RL 只能从「有时对有时错」的数据里学。
  • 一行 = 一个组（行按 rollout.n 展开成 n 个共享 uid 的样本），加行改变的是任务多样性 × 步数，不是批大小。
  • r3 分带：pass/pass 247、pass/fail 54、fail/fail 76、fail/pass 1；只取 base=pass 带，60 题 × 5 epochs = 300 步。
  • 「只有一行」与「每步赌解出」是两种失败同一个根：前者是多样性（加题即解），后者是单批可认证性（1000 行也救不了，每行仍要独立过闸）。
  • 当初一行是收尾口径：APPS 出不了方差（0/80），选一个已知解出率的载体题先打通链路——「打通链路优先于做对任务」。
证据：build_verl_pi_dataset.py:1-22 注释；r3 筛题记录（bands 247/54/76/1）；APPS 80/80 全灭实测。
清洗失败在框架路径里是 raise（fatal），在旧自研路径里是 report（重采样）——为什么接受这种不对称？追问：那框架路径会不会「更脆」？
一句话先答：语义没有变——两边都 fail-closed（不合格的数据绝不训练）；变的是失败的表达方式：框架路径里 raise 是唯一能让整批停在训练器之外的机制，再配重采样把「可重试的失败」接住。
  • 旧路径：门禁失败是一份 report（manager_certified: false），轮次重新采样——因为采样和门禁都是我们的代码，可以礼貌地重试。
  • 框架路径：raise 是框架 API 内表达「这批不可用」的唯一方式；raise 之后由 manager 的重采样层决定是否重画。
  • 看似「更脆」其实暴露了旧路径隐藏的问题：旧路径 1/4 解出率是运气（真实 ~1/16），样本从 4 扩到 16 后暴露的是采样预算墙，不是集成坏了。
证据：smoke24（漏斗 16→6→2 解出，批被 tuple/list bug 拒）；smoke25/26（1/16、0/16）；legacy 对照 stage_e_assemble.py:162 的 report 语义。
C踩坑与优化
讲一次「门禁永远不可能通过」的 bug。考察点：怎么定位一个两边都持久化、无法复现差异的失败
一句话先答：tuple != list。ProducerArtifact.from_dict 深冻结 payload，存证是 tuple，重建是 list，直接比较容器恒 False——smoke24 上四数组逐元素完全一致，批照样被拒。
  • 定位难点：两边都是持久化文件，事后无法复现「差异」；报错只说 "does not bind actual inference context"，不指 episode、不指字段——浪费一整轮 GPU 猜谜。
  • 修复一：training_sequence_matches 逐元素比较（_as_token_list 归一化），容器类型不参与判定。
  • 修复二：describe_sequence_difference 输出每字段长度 + 首个差异下标；「token 相同、容器不同」被如实报为比较 bug——把「不可诊断的失败」变成「自解释的失败」。
  • 元教训：比较语义要绑定数据的序列化语义（deep-freeze 是 from_dict 的行为，比较函数必须知道这件事）。
证据：sequence.py:98-164；commit 6ec0ad5；smoke24 记录。
讲一次「配置存在但从未生效」的 bug。考察点：静默失败的发现与防御
一句话先答：重试循环在自己 except 里 re-raise，max_attempts 看起来是重试配置、实际是单发——smoke26 一个零方差批直接终结了 run。
  • 为什么难发现：不崩溃、无栈、日志正常——只有第二次 attempt 才会到来的路径从未被执行。
  • 修复：重采样策略抽成独立纯函数 certify_with_resampling（不 import Ray/verl，CPU 可单测），白名单重试 + 拒绝落盘；commit bc06a5f。
  • 防御设计：让「值得测的决策」住在值得测的地方——它是框架侧管理器里唯一能脱离 GPU 验证的部分。
  • 白名单纪律：确定性违规第一次就 raise——重试要花一整轮 rollout 复现同一失败，还把症状报三遍。
证据：resampling.py:8-15 注释原话；smoke26 → smoke27（同配置跑通两步）对照。
一个「没有工具调用」的回合为什么从 raise 改成了合法样本？考察点：门禁比契约更严时会发生什么
一句话先答：无工具回合仍然是样本：有动作（策略自己的 token）、有任务结局、有 reward，PPO 训练需要的全有；raise 把它当故障，代价是把同批正在跑的兄弟样本一起扔掉。
  • 实测代价（smoke23）：认证本可给这个 episode 判 ELIGIBLE（score 0.0），但 raise 中止了整个 generate_sequences 的 gather，连带扔掉同批已进入第二次模型请求的 episode——一个弱样本被放大成全批损失。
  • 裁决权归还：「无学习信号」的裁决本来就在批门禁（零方差检查），不该由样本层越权。这样的批到批门禁依然是平批、依然会被重画——语义收敛。
  • 留痕：num_tool_rounds 保持事实可见，证据里看得到这是无观察回合。
证据：pi_loop.py:279-290 注释记录完整决策链；commit 33347d1。
元教训：门禁的严格度必须等于契约本身——更严不是更安全，是把裁决挪到了信息更少的位置。
目录布局上踩过哪些坑？episode 命名为什么长这样？考察点：文件系统即证据库的工程纪律
一句话先答：三代防撞 + 两个位置约束，全部来自真实故障：episode 目录 = session/gen-NNN/attempt-N/{run_id}-{slug}-{sample_token}，工作区必须住在整棵树之外。
  • 为什么不能只用 sample_token 命名：trainer 会多次调用 generate_sequences（校验 + 每 step），同样的任务、同样的 token 再来一遍会改写上一轮目录——episode writer 对已存在根 fail-closed，全批死。所以每次调用有 gen-NNN，每次 run 有 session_id（run_id + 时间戳 + pid）。
  • attempt 维度：重采样重画写新目录，旧 attempt 保持可审计。
  • 工作区两坑：放 episode 根之下，parents=True 提前建根，每个 episode 死在 orchestrator 的 mkdir(exist_ok=False)；放 attempt 目录旁边，批门禁把每个子目录当 episode。
  • dispatch-trace.jsonl：每 episode 派发一行（pid、attempt、sample_token、output_dir 是否已存在），O_APPEND 防并发覆写，诊断失败绝不打断 rollout。
证据：pi_loop.py:87-106、:122-150；verl_manager.py:140-149。
D异常与边界
verifier 崩了（基础设施失败）为什么不能给 reward=0？考察点：奖励完整性的定义
一句话先答：0 奖励是一个训练信号（「做错了」），基础设施失败不是信号（「没测成」）——把后者喂给训练器等于向梯度里注入谎言。
  • 只有终止性判定 PASSED/FAILED 才映射 1/0；其他一切（超时、输出缺失、状态码异常）一律 raise。
  • 批门禁同构约束：episode summary 必须有终止性判定，否则该 attempt 直接被拒。
  • 奖励一致性被复核：admitted-sequence 的 reward 必须等于 1.0 if PASSED else 0.0，框架返回的 rm_scores 也逐样本核对（L4）。
证据：pi_loop.py:293-304；verl_manager.py:289-294、:329-333。
一个吃满 token 预算的回合是错误吗？截断、中止、完成怎么区分？考察点：终止符语义 + 用框架语义对齐设计
一句话先答：吃满预算 = 截断，是一次合法的截断动作，照常训练——因为 verl 自己的 stock 多轮 loop 从不检查 EOS；中止（请求被取消）才不是回合，直接 raise。
  • 解码层三态：模型采样到自己的 EOS / 配置的停止条件 / 预算打满。只有第一种是「完成」，第三种是「截断」——解码层概念，不是 RL 概念；单轮里它不改变任何下游计算，多轮里它决定下一轮上下文。
  • 决定性证据：verl 的 tool_agent_loop.py:246 把所有生成 token 无条件标 mask=1，:254 只按长度收尾，全文件 grep 不到任何 EOS 检查——对齐框架语义不是妥协。
  • 实测依据（smoke22）：四个 episode 全部 {tokens: 3584, budget: 3584, terminated: false}——P0 策略从不主动吐终止符；坚持要求终止符 = 零可训练样本。
  • 留痕：每回合记 terminated/tokens/budget/stop_reason，episode 级汇总 truncated_turns；终止符缺席下一轮补回（mask=0）。
证据：native_transport.py:240-256；token_context.py:167-198（accept 注释含框架行号）；engine-notes/*.turns.jsonl。
引擎无法自报「我服务的是第几步权重」，身份怎么钉？考察点：如何处理无法消除的证据缺口
一句话先答：不让引擎自证，改让框架自己写出的 checkpoint 作证：engine_step = global_steps − 1，把 global_step_N/actor 整棵目录树哈希进 adapter_revision；引擎侧缺口如实落盘，不许当成已确认。
  • 缺口根源：checkpoint_engine.backend=naive 走 fsdp_workers.py:1735 的同步路径，update_weights 丢弃 global_steps，引擎侧永远报 None。
  • 三层兜底：轮级 round-policy.json → episode 级指纹随批下行 → 批级门禁校验单一指纹 == 本轮策略；引擎一旦真报步数，传输层立即校验（episode 内不变、等于期望值）。
  • 缺口记录：engine-notes/*.step.jsonl 逐调用写明 reason；extra_fields 暴露 unconfirmed_steps、engine_step_confirmed: false。
  • 反面教材：曾把 numpy 标量塞进 json.dumps → TypeError 逃逸成 502 团灭全批——证据通道自身的健壮性也是要设计的。
证据：native_transport.py:81-120、:209-219；verl_manager.py:165-184；smoke27 的 gen-001 digest == P1 实测。
清洗都过了，为什么还要再校验框架返回的批？查什么？考察点：信任边界——门禁的对手盘包括框架自身
一句话先答：认证的对象是落盘证据，训练器消费的是框架拼好的 tensor 批——两者之间隔着框架的填充/重组代码。L4 校验「框架没有动过我们认证过的任何东西」。
  • 数量：批大小不变；证据目录数 == 批大小（无未消费/缺失 episode）。
  • 身份：episode id 合法（非路径）且全局唯一；group_id == uid（框架没改 GRPO 分组）。
  • token：attention mask 内的 prompt/response 逐 token 等于认证序列。
  • 训练语义：response_mask 未被篡改、padding 位置 mask 全 0（不许训练填充）、rollout_log_probs 与原生 logprobs torch.equal、reward 逐样本一致。
证据：verl_manager.py:351-384（_verify_returned_batch 全文）。
一句话总结设计哲学：每条数据的三次「亮相」（落盘证据 → 认证序列 → 框架 tensor）必须逐位一致；任何一次对不上，宁可这一步不训练。
04 · Claim Red Lines

什么能说，什么绝对不能说。

面试里最容易翻车的不是技术细节，是口径。下面每一条都有实测证据背书或否定。

Can say · 01

机制闭环已验证

RayPPOTrainer 拥有循环，我们经四个官方扩展点接管 rollout 数据平面；smoke27 用 n=32 / max_attempts=3 跑两个框架 step（22m34s），step 2 的 rollout 消费 step 1 同步后的权重（框架 checkpoint 摘要作证）。

Can say · 02

数值证明在案

训练侧重算 logprob 与 rollout 侧原生 logprob Pearson 0.99957/0.99959；框架 reward 步空转（4.77e-05s），说明奖励确实由我们的 verifier 给出。

Can say · 03

清洗严格且可审计

批级五规则 + 返回批校验 + 白名单重采样，全部 fail-closed；rejected-attempt / certified-batch 落盘，lineage 可复查。

Can say · 04

规模化执行过

formal-r2 从 P12 连续 24 步（磁盘满在 step 18，同命令恢复）；r3 完成任务分带筛题（247/54/76/1）。

01

「训练有效 / 涨点了」holdout 33.33% vs P0 29.17% / P12 31.25%，Fisher p=0.826/1.000，n=48 不显著；2/32、1/32 是噪声。只能说「实验已按此功率设计」。

02

「这是一套完整的训练系统」五条件对照不满足：数据供给 ❌、跨 run 接线未实测 ⚠️、可移植 ⚠️、可评价 ❌、自愈 ⚠️；只验证过同步循环、单机双卡、colocated。

03

「任何任务都能训」APPS 0/80 全灭；只有解出率落在中间带的数据可用——这是数据供给问题，不是接入问题。

04

「verl 的 reward / advantage 是我们的」正好相反——我们绕过了 reward manager（如实说），advantage/优化器/同步全归框架。

回到准确表述 · The Accurate Claim
机制上完整跑通并有实测证据；作为日常可用的训练系统还不行——差的不是集成，是数据供给、跨 run 可续性和可评价性。
两个万能收尾：被问「所以到底接入了吗」用上一句；被问「清洗值得吗、重采样不浪费算力吗」答——「GRPO 的 advantage 只能来自组内真实散度，伪造信号等于训练噪声；浪费的算力买的是『进优化器的每个梯度都有证据』，formal-r2 的 24 连步与磁盘满恢复都靠这套纪律兜底。」
