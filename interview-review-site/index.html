模块一 · RL 数据生成：从任务行到可信 token 序列

数据生成分三层：任务侧（一行数据 = 一个 GRPO 组）、采样侧（每样本跑一次真实 Pi episode）、 token 层（账本 + 原生桥 + 序列组装）。三层共同保证一件事：进入清洗环节的每条样本，都是「策略在某一确定权重下真实生成」的完整证据。

1.1 任务侧：一行数据就是一个 GRPO 组 scripts/build_verl_pi_dataset.py

构建器从 evalplus 的 get_mbpp_plus()（378 题）取任务，一行一题。框架的 dataloader 会把每行按 rollout.n 复制成 n 份共享同一 uid 的样本——所以行就是组：同一道题的 n 次独立 episode，正是 GRPO 组相对 advantage 需要的分组。

scripts/build_verl_pi_dataset.py:44-71行 schema：框架需要的列 + 我们 loop 依赖的 extra_info
rows.append({
    "prompt": [                       # 框架要求该列存在；loop 实际从 extra_info 构建 Pi 指令
        {"role": "system", "content": "You are a coding agent working in a workspace."},
        {"role": "user",   "content": task_prompt},
    ],
    "data_source": "mbpp",            # 框架 reward 路由键（reward 由 loop 直接给，reward 路径被绕过）
    "reward_model": {"ground_truth": {"task_id": task_id, "entry_point": entry_point}},
    "extra_info": {                   # 我们 loop 的真实输入
        "index": index,               # 数据集默认全 0 会撞车，这里显式赋值
        "task_id": task_id, "task_slug": slug,
        "task_prompt": task_prompt, "group_id": args.group_id,
    },
    "agent_name": "pi_agent",         # 选择我们注册的 agent loop
})
# uid 刻意不写：RayPPOTrainer.fit 在按 n 展开前为每行生成新 uid，
# n 个 episode 天然共享一个组。

r3 筛题规则：为什么只选 base=pass 的题（这是「数据生成」里最重要的一个实验设计决策）

GRPO 方差门禁会把「全对/全错」的平批重采样重画；一个真正 p≈0 或 p≈1 的任务会耗尽 max_attempts， 该 step 永远过不去（resume 还会重放同一任务）——这叫平批死锁。所以任务先按 P0 SFT 模型在 evalplus 上的贪心状态分带： pass/pass 247 题、pass/fail 54、fail/fail 76、fail/pass 1；只从 base=pass 的带子里等距取题 （r2 实测该带在自家 agent loop 下成功率 15–65%，正落在「有时对有时错」的理想区间）。378 题全带 assert，verifier 对任意 Mbpp/N 都能打分。

1.2 采样侧：每个样本一次真实 Pi episode src/integrations/verl/pi_loop.py

PiAgentLoop(AgentLoopBase).run 是框架逐样本调用的入口。它不自己生成 token——它起一个真实的 Pi agent 子进程， 让 Pi 通过我们的代理去打 verl 的 vLLM 引擎，全程留下证据。

解析身份并命名 episode
从批次里读 manager 盖的章：pi_attempt（重采样轮次）、pi_sample_token（a{s}p{i}，因为 rollout.n 复制出的行除 uid 外无法区分）、pi_episode_root（本次 generate_sequences 专属目录）。episode 目录 = call_root / attempt-N / {run_id}-{task_slug}-{sample_token}（pi_loop.py:220-231）。
建工作区（在 attempt 目录之外）
episode_workspace() 把工作区放在 workspaces/{attempt}--{episode} 兄弟树上。两个约束都踩过坑：orchestrator 对 episode 根目录 fail-closed（mkdir(exist_ok=False)），预先创建会让每个 episode 死在 mkdir；批门禁把 attempt 目录下每个子目录当 episode，工作区混进去会被当成「缺证据的 episode」（pi_loop.py:87-106）。
起 Pi 子进程（bwrap 隔离）跑多轮工具循环
Pi ↔ 我们的模型代理 ↔ verl vLLM。Pi 永远不直接碰 vLLM——只有代理会把每轮的原生 token ids + logprobs 记成身份绑定的证据。工具集冻结为 read/bash/write/edit/ls，且校验实际请求的工具 schema 哈希 == 冻结值（native_transport.py:192）。
episode 内跑 verifier
Pi 结束后立刻在 episode 里跑 verify_mbpp_src.py（从题面抽 assert、跑 solution.py），产出 verifier_status ∈ {PASSED, FAILED}（pi_loop.py:442-448）。这是逐 episode 的第一道清洗，也是 reward 的唯一来源。
reward 映射与硬边界
PASSED→1.0，FAILED→0.0；其余一律 raise——基础设施失败不是合法的 0 奖励，绝不许把「没跑成」伪装成「做错了」喂给训练器（pi_loop.py:293-304）。

prompt/response ids、mask、logprobs、reward、组号、双 checksum 全部落盘；批门禁稍后从落盘证据重新认证，不信任内存对象（pi_loop.py:324-326）。extra_fields 还带 truncated_turns、unconfirmed_engine_steps、engine_closeout 等自证字段。

1.3 token 层：append-only 账本 + 原生 token 桥 token_context.py / native_transport.py

多轮 agent 对话要变成一条训练序列，最大的坑是上下文漂移：如果每轮都从 messages 重新渲染 prompt，之前模型生成的 token 就会被重新 tokenize 改写。 解法是一个不变式——prompt 就是账本：

账本不变式（由构造成立，不需要任何松弛）

prompti+1 = prompti + generationi（原生 token，逐字）+ observationi（新编码的上下文后缀）

  • 首轮 prompt 冻结自 apply_chat_template；之后只有新的观察块被编码（token_context.py:112-157）。
  • 每轮校验 Pi 没改历史：既有消息全文比对，新生成的 assistant 回合只比承重字段（tool_calls 必须一致；content 允许为空——实测 Pi 会把 content 置 null 只留 tool_calls，token_context.py:35-54）。
  • 模板边界校验：渲染前后必须满足 after.startswith(before)，防止模板改写历史（token_context.py:138-146）。
  • 回合终止符 <|im_end|> 被 vLLM 当特殊 token 吞掉不返还——账本记 terminator_stripped，下一轮把终止符作为纯上下文补回（mask=0，无 logprob，永不进 loss，token_context.py:149-157）。
src/integrations/verl/native_transport.py:196-208（节选）token 级 RPC：不走 /v1/chat/completions 文本，走 prompt_ids
prompt = self.context.prepare(payload["messages"], payload.get("tools", []))
budget = min(self.max_tokens, self.context.remaining)
params = dict(self.sampling_params)
params.update(max_tokens=budget, logprobs=True)
# 引擎必须停在回合终止符上：本策略不总是自己吐 im_end，
# 没有 stop 的话唯一的限制器就是预算
params["stop_token_ids"] = [self.context.turn_end_id]
output = await self.server_manager.generate(
    request_id=self.episode_id, prompt_ids=prompt, sampling_params=params
)
ids = list(output.token_ids)
probs = output.log_probs
if probs is None or len(probs) != len(ids) or not all(math.isfinite(p) for p in probs):
    raise ContractValidationError("missing or invalid native logprobs")

工具调用解析：提取，不修复（native_transport.py:16-50）

  • 实测（smoke16 十条真实生成）：vLLM 的 hermes parser 10/10 解析出 0 个工具调用——该策略输出裸 JSON 不带 <tool_call> 标签，只信上游 parser 等于没有工具循环。
  • 策略：parser 有结果时校验标签数与解析数一致（混合状态直接 raise）；无结果时回落到仓库唯一的严格提取器 src.capture.tool_calls——全仓库只有一种提取策略。
  • 不修复原则：未声明工具名 / 坏 JSON / 空 arguments 一律产出空，绝无「猜」。标签块被 parser 拒绝视为 malformed 而不是再解析一次。最新补丁（未提交 diff）：parser 自身抛异常（如 TypeError: unhashable type: 'dict'）时也回落严格提取器，坏抽样交给批门禁按真实 reward 裁决，而不是报废整批。

预算三态：预检、截断、中止（native_transport.py:152-177, 240-256）

  • can_serve 预检：进引擎之前问「下一轮还买得起吗」——买不起就以 context_budget 收束 episode，而不是让一次模型调用失败。实测 smoke16 有生成吃满整个 1024 预算，耗尽上下文是常态不是错误。
  • 截断（truncated）：吃满预算没吐终止符 = 一次合法的截断动作，照常入账（verl 自己的 loop 也这么训），truncated_turns 计数留痕。
  • 中止（aborted）：引擎因请求取消而停——这不是一个回合，直接 raise。
  • 引擎步数自证：引擎回报 global_steps 时校验其与期望一致且 episode 内不变；backend=naive 下引擎报 None，则逐 episode 写 step-note 记录这个已知缺口而不是掩盖（曾因 numpy 标量混进 json.dumps 变成 502 团灭全批）。

1.4 多轮 → 单序列组装：mask 是唯一的语义边界 src/integrations/verl/sequence.py

episode 结束后，_assemble 从 model-evidence.jsonl 里的逐调用 token 证据重建出一条 verl 训练序列。这个模块从不 tokenize 文本——它只拼接桥在真实运行中捕获的 token。

一条两轮工具调用的 episode 组装后的 token 条：
prompt首轮冻结
gen₁ mask=1原生 ids+logprobs
obs₁ mask=0工具观察+模板
gen₂ mask=1原生 ids+logprobs
obs₂ mask=0观察后缀
… mask=1
  • mask=1 的只有模型生成的原生 token（带真实 logprobs）；观察与模板分隔符是纯上下文，mask=0。
  • 观察位 logprob 用 0.0 显式占位——是「非概率」，所有统计必须经 mask 排除（sequence.py:30）。
  • 任何历史改写（压缩/截断/分支/回滚）→ history_rewritten=True → 拒绝整个 episode，绝不重 tokenize 收尾消息来圆（sequence.py:210-213）。
src/integrations/verl/sequence.py:202-244（节选）组装核心循环
for index, segment in enumerate(per_call_segments):
    if segment.get("history_rewritten", False):
        raise ContractValidationError(
            f"{field} rewrote generation history; episode is not trainable"
        )
    native_ids = _checked_int_list(segment.get("native_response_ids"), ...)
    native_logprobs = _checked_float_list(segment.get("native_response_logprobs"), ...)
    if len(native_logprobs) != len(native_ids):
        raise ContractValidationError(f"{field} response/logprob alignment invalid")
    context_suffix = _checked_int_list(segment.get("context_suffix_ids", ()), ...)

    response_ids.extend(native_ids)
    response_mask.extend([1] * len(native_ids))          # 模型自己的 token → 可训练
    response_logprobs.extend(native_logprobs)
    if context_suffix:
        response_ids.extend(context_suffix)
        response_mask.extend([0] * len(context_suffix))  # 观察/模板 → 纯上下文
        response_logprobs.extend([_OBSERVATION_LOGPROB_PLACEHOLDER] * len(context_suffix))
        tool_rounds += 1

为什么这条路能「无损」接上 verl

verl 的 _agent_loop_postprocess 对返回的 AgentLoopOutput 从不重新 tokenize：response_ids 原样右填充，完全信任 response_mask（1=LLM 生成，0=观察）和 response_logprobs。这与我们 AssembledSequence 的语义逐字段同构—— 所以经过认证的序列映射成 verl 的类型时零损失。这就是整个接入设计的支点。

2

模块二 · 数据清洗：认证不过，一步也不进训练器

清洗在本项目里不是一个后处理脚本，而是嵌在 generate_sequences 与训练器之间的门禁。它的契约是批级的 （单一行为策略、episode 唯一、组规模、任务绑定、组内奖励方差），而框架的 AgentLoopBase.run 是逐样本的—— 所以认证必须放在比 loop 高一层、比 trainer 低一层的 manager 上，且失败必须 fail-closed。

2.1 为什么门禁长在 manager 上 verl_manager.py:1-26 模块注释即答案

  • 粒度错配：GRPO 的组语义（同题 n 样本、组内方差）只有在凑齐整批后才能判定；逐样本的 loop 判不了。
  • 时机：CertifiedVerlAgentLoopManager.generate_sequences 在框架的生成调用返回前执行认证——认证在训练前、失败不能旁路，这是把门禁放这里的全部意义。
  • 归属：manager 从不算 advantage、不碰权重、不训练；它只做三件事——把当前轮策略注入批次、更新前验证整批、留下可审计的 lineage 记录（certified-batch-attempt{N}.json）。

2.2 三级清洗漏斗 + 一次最终校验

L1

↓ 每一 episode

↓ 整批凑齐后

    if len({task_ids_by_episode[e] for e in members}) != 1:
        raise ContractValidationError(f"group {group_id!r} mixes tasks")  # ④ 任务绑定
    if len({item.reward for item in items if item.group_id == group_id}) < 2:
        raise DegenerateBatchError(                                       # ⑤ 组内方差
            f"group {group_id!r} has no intra-group reward variance")

规则⑤为什么是 DegenerateBatchError 而不是普通 raise

GRPO 的 advantage 是组相对散度：A_i = (r_i − mean(r_group)) / std(r_group)。全同奖励的组减均值后恒为 0， 对优化器是纯噪声。这样的批拒绝是正确的，终止整个 run 是错的——什么都没被消耗，诚实的动作是重画一批。 所以「无方差」被编码成独立异常类型，成为重采样策略唯一的批级触发器。

2.4 重采样策略：只重试「抽签性质」的失败 src/integrations/verl/resampling.py

重采样策略被刻意放在独立模块、远离 Ray 和 verl——它是框架侧唯一值得脱离 GPU 测试的决策，而它防的失败是沉默的（见 2.6 的坑一）。

src/integrations/verl/resampling.py:61-77重试白名单：DegenerateBatchError + RetryableRolloutError
for attempt in range(max_attempts):
    try:
        batch = await generate(attempt)          # 必须先盖 attempt 章 → 写进新 episode 目录
        certificate = certify(batch, attempt)

失败类型处置理由
组内零方差（DegenerateBatchError）重画，计入 max_attempts抽签性质：换一批样本可能就有信号；未消耗任何东西
单 episode 瞬态失败（RetryableRolloutError）整 attempt 重画桥/解析的偶发故障是「这一抽」的属性，不是证据矛盾；attempt 目录独立，失败轮可审计
确定性契约违规（其余 ContractValidationError）第一次就 fail，不重试重试要花一整轮 rollout 才能复现同一失败，而且把同一个症状报告三遍；确定性问题要的是修代码
max_attempts 耗尽终止 run，报最后一次错误诚实失败优于静默跳过；resume 从同一任务重放，会再暴露一次

重画的可审计性设计

  • attempt 号在生成前盖进批次（_stamp_attempt），所以重画写的是全新 episode 目录，不会与被拒 attempt 撞名（verl_manager.py:253-270）。
  • 每次拒绝落盘 rejected-attempt{N}.json（reason + message + manager_version）——「重画过的批次不能伪装成一次过」（verl_manager.py:235-251）。
  • 通过后落盘 certified-batch-attempt{N}.json，附 batch_checksum（sha256），lineage 可复查（verl_manager.py:386-395）。

2.6 两个著名的坑（面试讲这两个最加分）

坑一：tuple != list，门禁永远不可能通过（smoke24）

ProducerArtifact.from_dict 会对 payload 深度冻结，存下来的数组是 tuple；重新组装出来的是 list。 而 Python 里 tuple == list 恒为 False——直接比较容器，门禁永远拒绝。smoke24 上四个数组逐元素完全一致 （同长度、无差异下标、list(stored) == list(rebuilt)），批照样被拒，且事后从 episode 目录完全看不出原因——两边都是持久化的。

def training_sequence_matches(stored, expected):

A · 设计动机

动机verl 自带 tool_agent_loop，为什么要自己写一个 AgentLoop？追问：自写的边界在哪，哪些坚决不碰？
一句话先答：框架的 loop 能跑多轮工具调用，但给不了我们需要的证据平面——逐调用原生 token ids/logprobs、身份绑定、episode 内 verifier 与认证序列；我们换的是 loop 的「策略」，不是 loop 的「机器」。
  • 证据需求：训练要的不是 chat 文本，是「策略在某确定权重下逐 token 的真实生成」。所以 Pi 只能经我们的代理访问引擎（代理记录每轮原生 ids+logprobs 为身份绑定证据），token 走 AsyncLLMServerManager.generate(prompt_ids=…) 的 token RPC。
  • mask 语义：多轮工具调用要区分「模型生成的」与「喂回去的观察」，response_mask 是我们的语义，框架信任它——这正好是 _agent_loop_postprocess 不重 tokenize 的原因能被利用的地方。
  • 奖励语义：reward 必须来自 episode 内我们自己的 verifier（PASSED/FAILED→1/0），verl 的 reward manager 被绕过——这一点要如实说（框架的 reward timing 实测 4.77e-05s，是空转）。
  • 边界：训练循环、advantage、PPO-clip、FSDP2、优化器、权重同步、checkpoint、vLLM 引擎与调度——一行不替代，全是框架的（smoke27 实测 update_actor 186.8/188.1s、update_weights 2.90/2.83s）。
证据：四个官方扩展点（§0 表格）；src/integrations/verl/pi_loop.py:1-22 模块注释；归属表见 README §5.4 的 claim 范围。
可能追问：「那为什么不往 verl 提 PR？」——我们的需求（证据捕获、fail-closed 认证）是数据平面的私货，不是通用需求；挂在扩展点上升级框架零成本。
动机认证/清洗为什么放在 manager 层，而不是每个样本的 loop 里？追问：放在 trainer 侧不行吗？
一句话先答：我们的契约是批级的（单一行为策略、episode 唯一、组规模、任务绑定、组内方差），而 AgentLoopBase.run 是逐样本的——组语义只有凑齐整批才判得了。
  • 放在 manager（generate_sequences 内、返回前），认证就落在「生成之后、trainer 消费之前」，失败无法被旁路：raise 会让这次生成调用直接失败，trainer 拿不到批。
  • 放在 trainer 侧（比如 reward/advantage 阶段）则太晚：批已经进了训练数据管线，拒绝意味着 trainer 代码也要改——而我们对训练器是零侵入的。
  • manager 只做三件事：注入当前轮策略、认证整批、留 lineage 记录；不碰 advantage、不碰权重。
证据：src/integrations/verl/verl_manager.py:12-25（模块注释就是标准答案）；门禁实现 manager.py:77-132。
动机GRPO 下零方差批为什么必须丢弃？丢弃后为什么是「重画」而不是「跳过这一步」？追问：能不能给个小的默认 advantage？
一句话先答：GRPO 的 advantage 是组相对散度，全同奖励的组减均值后恒为 0，这批数据对优化器是无信号噪声；重画是因为什么都没被消耗，且这是抽签性质的问题——下一批可能有信号。
  • 数学：A_i = (r_i − mean) / std，组内全 1 或全 0 → mean=r_i、std=0 → advantage 无定义/全零。
  • 不能造信号：给默认 advantage 等于把「没有证据的梯度」注入更新，与 fail-closed 的清洗哲学直接冲突。
  • 重画成本 = 一次 rollout；拒绝成本 = 一个 step。实测 Mbpp/118 解出率约 1/16，n=8 时平批概率不低，重采样是常规路径不是异常路径——r3 甚至把 max_attempts 设到 20。
  • 重画必须可审计：attempt 号预盖进批次、rejected-attempt{N}.json 落盘，防止重画的批伪装成一次过。
证据：resampling.py:1-15 模块注释；r3 筛题规则（base=pass 带 15–65% 成功率）正是为了让重采样保持低频。
可能追问：「max_attempts 耗尽怎么办？」——终止 run 并报最后一次错误；resume 会重放同一任务再暴露一次，这逼你换数据而不是掩盖。
动机为什么要做「prompt 即账本」的 append-only 设计？追问：严格契约是什么，为什么最后不需要松弛它？
一句话先答：多轮对话若每轮从 messages 重新渲染 prompt，历史里的模型 token 就会被重新 tokenize 改写——训练信号就不再对应真实生成。账本让 prompt_{i+1} = prompt_i + gen_i + obs_i 由构造成立，原定的严格契约无需任何松弛。
  • 只有两种编码发生：首轮冻结 prompt、每轮新观察后缀；模型已生成的 token 永远逐字进账本。
  • 防御：既有消息全文比对；新 assistant 回合比承重字段（tool_calls 必须一致、content 空不判改写——实测 Pi 回 content: null）；模板边界 after.startswith(before)。
  • 终止符问题：vLLM 不返还特殊 stop token，<|im_end|> 缺席分不清「结束」与「截断」——账本记 terminator_stripped，下轮把终止符作为纯上下文补回（mask=0、无 logprob、永不进 loss）。
  • 曾经的替代方案（按调用忠实分解再拼接）连同它的三个阻塞点一起被账本路线取代，因为账本让分解恒等成立。
证据：token_context.py:1-11、:112-157；实测 smoke16 真实消息通过守卫且仅追加 20 个后缀 token。

B · 技术选型与对比

选型rollout 走 token 级 RPC 而不是 OpenAI chat API，为什么？追问：由此多出了哪些必须自己处理的问题？
一句话先答：chat API 只给文本，训练要的是每轮的原生 token ids 和 logprobs——这是行为策略证据（BEHAVIOR_LOGPROBS）的唯一来源，也绕开任何 decode/re-encode 漂移。
  • token RPC 直接拿到 token_ids + log_probs，且 logprobs 逐 token 校验（数量对齐、全部有限），缺失即 raise。
  • 代价是自己接管了协议层：stop 控制（stop_token_ids=[im_end]）、预算（min(max_tokens, remaining)）、上下文拼接（账本）、工具调用解析（上游 parser 不可靠，见下题）、特殊 token 不返还的处理。
  • 采样参数显式进身份：sampling_fingerprint = sha256({temperature, top_p})，与策略指纹一起构成「这批样本是谁、在什么采样配置下生成」的完整回答。
证据：native_transport.py:188-208；E 阶段数值证明：rollout 侧 logprob 与训练侧重算 Pearson 0.99957/0.99959。
选型工具调用解析为什么不能只信 vLLM 的 tool parser？「不修复」原则是什么？追问：parser 自己抛异常呢？
一句话先答：smoke16 实测该策略 10/10 的生成里 hermes parser 解析出 0 个调用（模型输出裸 JSON 不带标签）——只信它就没有工具循环；同时解析器只做提取，绝不修复，坏输出交给奖励与批门禁去裁决。
  • 三级策略：上游有结果 → 校验标签数与解析数一致（混合状态 raise，防止半信半疑）；上游无结果但有标签 → 视为 malformed（parser 拒绝过的东西不可信）；全无 → 回落仓库唯一的严格提取器 src.capture.tool_calls（全仓库一种提取策略，不是两套）。
  • 不修复：未声明工具名 / 坏 JSON / 空 arguments → 产出空，无猜测。修复会制造「模型没说过的话」，污染行为策略证据。
  • 最新兜底：parser 自身抛异常（TypeError: unhashable type: 'dict' 实测出现过）→ 同样回落严格提取器——一个坏抽样不应报废整批，让批门禁按真实 reward 说话。
证据：native_transport.py:16-50（_tool_calls 及其注释）；token_context.py:16-32（工具参数 JSON 校验，坏参即 raise）。
选型数据集只有几十行时，「加数据」到底改变了什么？为什么筛掉 fail/fail 的题？追问：一行数据为什么不是意外？
一句话先答：train_batch_size=1 时行数 = 步数（1 行 × 5 epochs = 5 步，且是不同的题）；筛掉 fail/fail 是因为 p≈0 的题永远全错、必然平批死锁——RL 只能从「有时对有时错」的数据里学。
  • 一行 = 一个组（行按 rollout.n 展开成 n 个共享 uid 的样本），所以加行改变的是任务多样性 × 步数，不是批大小。
  • r3 分带（P0 在 evalplus 贪心状态）：pass/pass 247、pass/fail 54、fail/fail 76、fail/pass 1；只取 base=pass 带（r2 实测 15–65% 成功率），60 题 × 5 epochs = 300 步。
  • 「只有一行」与「每步赌解出」是两种失败同一个根：前者是多样性（加题即解），后者是单批可认证性（1000 行也救不了，每行仍要独立过闸）。
  • 当初一行是收尾口径：APPS 出不了方差（0/80），选一个已知解出率的载体题先把链路打通——用户授权过「打通链路优先于做对任务」。
证据：build_verl_pi_dataset.py:1-22 注释；r3 筛题记录（bands 247/54/76/1）；APPS 80/80 全灭实测。
选型清洗失败在框架路径里是 raise（fatal），在旧自研路径里是 report（重采样）——为什么接受这种不对称？追问：那框架路径会不会「更脆」？
一句话先答：语义没有变——两边都 fail-closed（不合格的数据绝不训练）；变的是失败的表达方式：框架路径里 raise 是唯一能让整批停在训练器之外的机制，再配重采样把「可重试的失败」接住。
  • 旧路径：门禁失败是一份 report（manager_certified: false），轮次重新采样——因为旧路径里「采样」和「门禁」都是我们的代码，可以礼貌地重试。
  • 框架路径：raise 是框架 API 内表达「这批不可用」的唯一方式；raise 之后由 manager 的重采样层决定是否重画（DegenerateBatchError / RetryableRolloutError）。
  • 看似「更脆」的框架路径其实暴露了旧路径隐藏的问题：旧路径 1/4 的解出率是运气（真实 ~1/16），样本从 4 扩到 16 后暴露的是采样预算墙，不是集成坏了。
证据：smoke24（漏斗 16→6→2 解出，批被 tuple/list bug 拒）；smoke25/26（1/16、0/16）；legacy 对照 stage_e_assemble.py:162 的 report 语义。

C · 踩坑与优化

踩坑讲一次「门禁永远不可能通过」的 bug。考察点：怎么定位一个两边都持久化、无法复现差异的失败
一句话先答：tuple != list。ProducerArtifact.from_dict 深冻结 payload，存证是 tuple，重建是 list，直接比较容器恒 False——smoke24 上四数组逐元素完全一致，批照样被拒。
  • 定位难点：两边都是持久化文件，事后无法复现「差异」；报错信息只说 "does not bind actual inference context"，不指 episode、不指字段——浪费了一整轮 GPU 猜谜。
  • 修复一：training_sequence_matches 逐元素比较（_as_token_list 归一化），容器类型不参与判定。
  • 修复二：describe_sequence_difference 输出每字段长度 + 首个差异下标；「token 相同、容器不同」被如实报为比较 bug——把「不可诊断的失败」变成「自解释的失败」。
  • 沉淀的元教训：比较语义要绑定数据的序列化语义（deep-freeze 是 from_dict 的行为，比较函数必须知道这件事）。
证据：sequence.py:98-164；commit 6ec0ad5；smoke24 记录。
踩坑讲一次「配置存在但从未生效」的 bug。考察点：静默失败的发现与防御
一句话先答：重试循环在自己 except 里 re-raise，max_attempts 看起来是重试配置、实际是单发——smoke26 一个零方差批直接终结了 run。
  • 为什么难发现：不崩溃、无栈、日志正常——只有第二次 attempt 才会到来的路径从未被执行。
  • 修复：重采样策略抽成独立纯函数 certify_with_resampling（不 import Ray/verl，CPU 可单测），白名单重试 + 拒绝落盘；commit bc06a5f。
  • 防御设计：让「值得测的决策」住在值得测的地方——它是框架侧管理器里唯一能脱离 GPU 验证的部分。
  • 白名单纪律：确定性违规第一次就 raise——重试要花一整轮 rollout 复现同一失败，还把症状报三遍。
证据：resampling.py:8-15 注释原话（"looks like a retry loop and behaves like a single shot"）；smoke26 → smoke27（同配置跑通两步）对照。
踩坑一个「没有工具调用」的回合为什么从 raise 改成了合法样本？考察点：门禁比契约更严时会发生什么
一句话先答：无工具回合仍然是样本：有动作（策略自己的 token）、有任务结局、有 reward，PPO 训练需要的全有；raise 把它当故障，代价是把同批正在跑的兄弟样本一起扔掉。
  • 实测代价（smoke23）：ON_POLICY_RL 认证本可给这个 episode 判 ELIGIBLE（score 0.0），但 raise 中止了整个 generate_sequences 的 gather，连带扔掉同批已进入第二次模型请求的 episode——一个弱样本被放大成全批损失。
  • 裁决权归还：「无学习信号」的裁决本来就在批门禁（零方差检查），不该由样本层越权。这样的批到批门禁依然是平批、依然会被重画——语义收敛。
  • 留痕：num_tool_rounds 保持事实可见，证据里看得到这是无观察回合。
证据：pi_loop.py:279-290 注释记录了完整决策链；commit 33347d1。
元教训：门禁的严格度必须等于契约本身——更严不是更安全，是把裁决挪到了信息更少的位置。
踩坑目录布局上踩过哪些坑？episode 命名为什么长这样？考察点：文件系统即证据库的工程纪律
一句话先答：三代防撞 + 两个位置约束，全部来自真实故障：episode 目录 = session/gen-NNN/attempt-N/{run_id}-{slug}-{sample_token}，工作区必须住在整棵树之外。
  • 为什么不能只用 sample_token 命名：trainer 会多次调用 generate_sequences（训练前校验 + 每个 step），同样的任务、同样的 token 再来一遍会把上一轮目录改写——episode writer 对已存在根目录 fail-closed，全批死。所以每次调用有 gen-NNN，每次 run 有 session_id（run_id + 时间戳 + pid）。
  • attempt 维度：重采样重画必须写新目录，旧 attempt 保持可审计。
  • 工作区两坑：放在 episode 根之下，parents=True 会提前把根建出来，每个 episode 死在 orchestrator 的 mkdir(exist_ok=False)；放在 attempt 目录旁边，批门禁会把每个子目录当 episode，读出「缺证据的 episode」。
  • dispatch-trace.jsonl：每个 episode 派发一行（pid、attempt、sample_token、output_dir 是否已存在），O_APPEND 防并发覆写，且诊断失败绝不打断 rollout——「重复派发」和「盖错章」从此可分辨。
证据：pi_loop.py:87-106（episode_workspace 注释）、:122-150（dispatch trace）；verl_manager.py:140-149（generation 目录注释）。

D · 异常与边界

边界verifier 崩了（基础设施失败）为什么不能给 reward=0？考察点：奖励完整性的定义
一句话先答：0 奖励是一个训练信号（「做错了」），基础设施失败不是信号（「没测成」）——把后者喂给训练器等于向梯度里注入谎言。
  • 只有终止性判定 PASSED/FAILED 才映射 1/0；其他一切（verifier 超时、输出缺失、状态码异常）一律 raise。
  • 批门禁侧同构约束：episode summary 必须有终止性 verifier 判定，否则该 attempt 直接被拒（_certify_from_evidence 校验 verifier_status ∈ {PASSED, FAILED}）。
  • 奖励一致性也被复核：admitted-sequence 的 reward 必须等于 1.0 if PASSED else 0.0，框架返回的 rm_scores 也逐样本核对（L4）。
证据：pi_loop.py:293-304；verl_manager.py:289-294、:329-333。
边界一个吃满 token 预算的回合是错误吗？截断、中止、完成怎么区分？考察点：终止符语义 + 用框架语义对齐设计
一句话先答：吃满预算 = 截断，是一次合法的截断动作，照常训练——因为 verl 自己的 stock 多轮 loop 从不检查 EOS；中止（请求被取消）才不是回合，直接 raise。
  • 解码层三态：模型采样到自己的 EOS / 配置的停止条件 / 预算打满。只有第一种是「完成」，第三种是「截断」——这是解码层概念，不是 RL 概念，单轮 RLHF 里它不改变任何下游计算，多轮里它决定下一轮上下文。
  • 决定性证据：verl 的 tool_agent_loop.py:246 把所有生成 token 无条件标 mask=1，:254 只按长度收尾，全文件 grep 不到任何 EOS 检查。对齐框架语义不是妥协。
  • 实测依据（smoke22）：四个 episode 全部 {tokens: 3584, budget: 3584, terminated: false}——P0 策略从不主动吐终止符；坚持要求终止符 = 零可训练样本。
  • 留痕：每回合记 terminated/tokens/budget/stop_reason（turns note），episode 级汇总 truncated_turns；终止符缺席用 terminator_stripped 在下一轮上下文里补回（mask=0）。
证据：native_transport.py:240-256；token_context.py:167-198（accept 的注释含框架行号）；engine-notes/*.turns.jsonl。
边界引擎无法自报「我服务的是第几步权重」，身份怎么钉？考察点：如何处理无法消除的证据缺口
一句话先答：不让引擎自证，改让框架自己写出的 checkpoint 作证：engine_step = global_steps − 1，把 global_step_N/actor 整棵目录树哈希进 adapter_revision；引擎侧的缺口如实落盘记录，不许当成已确认。
  • 缺口根源：checkpoint_engine.backend=naive（出货默认）走 fsdp_workers.py:1735 的同步路径，update_weights 丢弃 global_steps，引擎侧永远报 None。
  • 三层兜底：轮级 round-policy.json → episode 级策略指纹随批下行 → 批级门禁校验单一指纹 == 本轮策略；引擎一旦真的报了步数，传输层立即校验（episode 内不变、等于期望值）。
  • 缺口记录：engine-notes/*.step.jsonl 逐调用写明 reason；extra_fields 暴露 unconfirmed_steps、engine_step_confirmed: false。
  • 反面教材：曾把 numpy 标量塞进 json.dumps → TypeError 逃逸成 502 团灭全批——证据通道自身的健壮性也是要设计的。
证据：native_transport.py:81-120（_note_unconfirmed_step）、:209-219；verl_manager.py:165-184；smoke27 的 gen-001 digest == P1 实测。
边界清洗都过了，为什么还要再校验框架返回的批？查什么？考察点：信任边界——门禁的对手盘包括框架自身
一句话先答：认证的对象是落盘证据，训练器消费的是框架拼好的 tensor 批——两者之间隔着框架的填充/重组代码。L4 校验「框架没有动过我们认证过的任何东西」。
  • 数量：批大小不变；证据目录数 == 批大小（无未消费/缺失 episode）。
  • 身份：episode id 合法（非路径）且全局唯一；group_id == uid（框架没改 GRPO 分组）。
  • token：attention mask 内的 prompt/response 逐 token 等于认证序列。
  • 训练语义：response_mask 未被篡改、padding 位置 mask 全 0（框架不许训练填充）、rollout_log_probs 与原生 logprobs torch.equal、reward 逐样本一致。
证据：verl_manager.py:351-384（_verify_returned_batch 全文）。
一句话总结设计哲学：从生成到更新，每一条数据的三次「亮相」（落盘证据 → 认证序列 → 框架 tensor）必须逐位一致；任何一次对不上，宁可这一步不训练。
4

说法红线：什么能说，什么不能说

面试里最容易翻车的不是技术细节，是口径。这张表每条都有实测证据背书或否定。

✅ 能说（有实测证据）

  • 机制闭环已验证：verl 的 RayPPOTrainer 拥有循环，我们经四个官方扩展点接管 rollout 数据平面；smoke27 用 n=32 / max_attempts=3 跑了两个框架 step（22m34s），step 2 的 rollout 消费了 step 1 同步后的权重（框架 checkpoint 摘要作证）。
  • 数值证明：训练侧重算 logprob 与 rollout 侧原生 logprob Pearson 0.99957/0.99959；框架 reward 步空转（4.77e-05s），说明奖励确实由我们的 verifier 给出。
  • 清洗严格性：批级五规则 + 返回批校验 + 白名单重采样，全部 fail-closed 且可审计（rejected-attempt / certified-batch 落盘）。
  • 规模化执行：formal-r2 从 P12 连续 24 步（磁盘满在 step 18，同命令恢复）；r3 完成任务分带筛题（247/54/76/1）。

❌ 不能说（会被证据当场拆穿）

  • 「训练有效/涨点」：holdout 33.33% vs P0 29.17% / P12 31.25%，Fisher p=0.826/1.000，n=48 不显著；2/32、1/32 是噪声。只能说「实验已按此功率设计」，不能说有效。
  • 「完整训练系统」：五条件对照（数据供给 ❌、跨 run 接线未实测 ⚠️、可移植 ⚠️、可评价 ❌、自愈 ⚠️）不满足；只验证过同步循环、单机双卡、colocated。
  • 「任何任务都能训」：APPS 0/80 全灭；只有解出率落在中间带的数据可用——这是数据供给问题，不是接入问题。
  • 「verl 的 reward/ advantage 是我们的」：正好相反——我们绕过了 reward manager（如实说），advantage/优化器/同步全归框架。

两个万能收尾句

  • 被问「所以到底接入 verl 了吗？」——「机制上完整跑通并有实测证据；作为日常可用的训练系统还不行。差的不是集成，是数据供给、跨 run 可续性和可评价性。」
  • 被问「这套清洗/门禁值得吗？重采样不浪费算力吗？」——「GRPO 的 advantage 只能来自组内真实散度，伪造信号等于训练噪声；浪费的那部分算力买的是『进优化器的每个梯度都有证据』，formal-r2 的 24 连步与磁盘满恢复都靠这套纪律兜底。」
