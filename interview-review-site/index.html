Task Screening · r3 筛题规则（最重要的实验设计决策）
  • 平批死锁规则：方差门禁会把全对/全错批重画；p≈0 或 p≈1 的任务会耗尽 max_attempts，该 step 永远过不去（resume 还重放同一任务）。
  • 分带（P0 在 evalplus 的贪心状态）：pass/pass 247、pass/fail 54、fail/fail 76、fail/pass 1；只从 base=pass 带等距取题。

先自己说一遍，再展开对照。

train_batch_size=1 时，「加一行数据」到底改变了什么？
先答：行数 = 步数（1 行 × 5 epochs = 5 步，且是不同的题）；一行 = 一个组（按 rollout.n 展开成 n 个共享 uid 的样本）。
加行改变的是任务多样性 × 步数，不是批大小。「只有一行」当初是收尾口径：APPS 出不了方差（0/80），选已知解出率的载体题先打通链路。
证据：build_verl_pi_dataset.py:1-22 注释。
为什么筛掉 fail/fail 的题？
先答：p≈0 的题永远全错 → 必然零方差 → 平批死锁；RL 只能从「有时对有时错」的数据里学。
分带后只取 base=pass 带（15–65%），让重采样保持低频。
证据：r3 筛题记录（bands 247/54/76/1）。
verifier 崩了（基础设施失败）为什么不能给 reward=0？
先答：0 奖励是训练信号（「做错了」），基础设施失败不是信号（「没测成」）——喂给训练器等于向梯度注入谎言。
只有终止性判定才映射 1/0；批门禁侧同构校验 summary 必须有终止性判定，reward 与判定的一致性在 L2/L4 复核。
证据：pi_loop.py:293-304；verl_manager.py:289-294、:329-333。
Step 3 / 6 · 数据生成（下）

多轮对话怎么变成一条「不撒谎」的训练序列？

核心是一个不变式：prompt 即账本（append-only）。每轮只有模型生成的原生 token（mask=1）可训练；观察与模板后缀是纯上下文（mask=0）。组装模块从不 tokenize 文本，只拼接桥在真实运行中捕获的 token。

Ledger · 账本不变式与防线

prompt[i+1] = prompt[i] + generation[i]（原生 token，逐字） + observation[i]（新编码的上下文后缀）

  • 由构造成立：只有两种编码发生——首轮冻结 prompt、每轮新观察后缀；已生成 token 永远逐字进账本，无需松弛任何严格契约。
  • 防线：既有消息全文比对；新 assistant 回合只比承重字段（tool_calls 必须一致；content 空不判改写——实测 Pi 回 content: null）；模板边界 after.startswith(before)。
  • 终止符补回：vLLM 不返还特殊 stop token，<|im_end|> 缺席分不清「结束/截断」——记 terminator_stripped，下一轮把终止符作为 mask=0 纯上下文补回，永不进 loss（token_context.py:149-157）。

✓ 自测 · 第 3 节

先自己说一遍，再展开对照。

「prompt 即账本」解决了什么问题？为什么最后不需要松弛严格契约？
先答：避免每轮重新渲染 prompt 造成历史 token 被重 tokenize 改写；账本让 prompt_{i+1}=prompt_i+gen_i+obs_i 由构造成立。
所以原定的严格契约天然为真，不需要任何 relaxation（曾考虑的按调用忠实分解路线被整体取代）。
证据：token_context.py:1-11、:112-157；smoke16 实测仅追加 20 个后缀 token。
吃满 token 预算的回合是错误吗？截断/中止/完成怎么区分？
先答：截断是合法动作，照常训练——对齐 verl 自身语义（stock loop 从不查 EOS）；中止（请求被取消）才 raise。
解码层三态：模型吐 EOS（完成）/ 停止条件 / 预算打满（截断）。每回合留痕 terminated/tokens/budget/stop_reason，episode 级汇总 truncated_turns。
证据：native_transport.py:240-256；token_context.py:167-198。
观察位的 logprob 填什么？怎么保证它不进损失？
先答：0.0 显式占位——语义是「非概率」；mask=0 让所有损失与统计天然排除它。
占位保证数组对齐，mask 保证损失正确——两个机制各司其职（sequence.py:30, :241-243）。
Step 4 / 6 · 数据清洗

什么样的批才配进训练器？不合格时发生什么？

清洗不是后处理脚本，而是嵌在 generate_sequences 与训练器之间的门禁。fail-closed：认证不过，一步也不进训练器。重采样只重试「抽签性质」的失败——其余第一次就 fail。

Why · 规则⑤为什么独立成 DegenerateBatchError
  • GRPO advantage 是组相对散度：A_i = (r_i − mean) / std；全同奖励 → 恒 0，对优化器是纯噪声。拒绝是正确的，终止整个 run 是错的——什么都没被消耗。
  • 实测 Mbpp/118 解出率 ≈ 1/16，n=8 时平批不罕见——重采样是常规路径不是异常路径（r3 把 max_attempts 设到 20）。
  • 重画必须可审计：attempt 号生成前盖进批次（_stamp_attempt，verl_manager.py:253-270）→ 重画写全新目录；每次拒绝落盘 rejected-attempt{N}.json——「重画过的批不能伪装成一次过」（:235-251）；通过后落盘 certified-batch 附 sha256。

  • 问题：on-policy RL 要求行为策略 == 目标策略；但 checkpoint_engine.backend=naive 下引擎无法自报「我服务的是第几步权重」。
  • 解法：engine_step = global_steps − 1；把 global_step_N/actor 整棵目录树哈希进 adapter_revision，policy_generation = P{engine_step}；指纹随批下行，传输层逐调用校验。
  • 三层绑定：轮级 round-policy.json → episode 级指纹进 identity 与证据 → 批级门禁规则①校验单一指纹。
  • smoke27 实测：generation-1 的 rollout 消费 global_step_1/actor 的摘要——「更新后再采样」由框架自己写出的 checkpoint 作证。引擎侧缺口如实写 engine-notes/*.step.jsonl，不许当成已确认。

哪两类错误可以重画？为什么确定性违规第一次就 fail？
先答：DegenerateBatchError（零方差）与 RetryableRolloutError（瞬态）——都是「这一抽」的属性；确定性违规是证据矛盾，重试只会复现。
重试的代价是一整轮 rollout + 把同一症状报三遍；确定性问题要的是修代码。
证据：resampling.py:39-58 docstring。
零方差批为什么必须重画而不是跳过/给默认 advantage？
先答：advantage = 组相对散度，全同奖励恒 0，是纯噪声；造信号违反 fail-closed；重画因为什么都没被消耗。
实测 1/16 解出率下重采样是常规路径，r3 max_attempts=20。
证据：resampling.py:1-15。
引擎不自报步数时，「这批样本是谁生成的」怎么钉？
先答：让框架自己写出的 checkpoint 作证：global_step_N/actor 整棵树哈希进 adapter_revision + 指纹三层绑定；引擎侧缺口逐 episode 记录。
smoke27 的 gen-001 digest == P1 证明 step 2 消费了 step 1 同步后的权重。
证据：verl_manager.py:165-184；native_transport.py:81-120。
Step 5 / 6 · 踩坑复盘

这条链路上最值钱的故事——面试讲出来就是加分项。

三个真实故障 + 一组工程纪律，每个都有 commit 与 run 证据。考察点不是「你踩过坑」，而是你怎么定位、怎么修、沉淀了什么原则。

「tuple != list，门禁永远不可能通过。」smoke24 · 难点：两边都持久化，事后无法复现差异
ProducerArtifact.from_dict 会对 payload 深度冻结：存证是 tuple，重建是 list，直接比较容器恒 False——四数组逐元素完全一致，批照样被拒。修复一：training_sequence_matches 逐元素比较，容器类型不参与判定；修复二：describe_sequence_difference 输出每字段长度 + 首个差异下标，「token 相同、容器不同」被如实报成比较 bug——修复前报错不指 episode 不指字段，代价一整轮 GPU 猜谜。证据：sequence.py:98-164 · commit 6ec0ad5。元教训：比较语义要绑定数据的序列化语义。
「在自己 except 里 re-raise 的重试 = 单发。」smoke26 · 静默失败：不崩溃、无栈，只是让 max_attempts 失效
旧版 attempt 循环在 except 分支直接再抛——看起来像重试循环，行为是单发：一个零方差批直接终结整个 run。修复：重采样策略抽成独立纯函数 certify_with_resampling（不 import Ray/verl，CPU 可单测），白名单重试 + 拒绝落盘。沉淀的原则：让值得测的决策住在值得测的地方。证据：resampling.py:8-15 注释原话 “looks like a retry loop and behaves like a single shot” · commit bc06a5f。
「一个没有工具调用的回合，把整批炸了。」smoke23 · 考察点：门禁比契约更严时会发生什么
无工具回合仍是样本：有动作、有结局、有 reward。但当时 raise 中止了整个 generate_sequences 的 gather，连带扔掉同批已进入第二次模型请求的 episode——一个弱样本被放大成全批损失。修复：裁决权归还批门禁（无信号批到 L3 依然是平批、依然重画——语义收敛）；num_tool_rounds 留痕。证据：pi_loop.py:279-290 · commit 33347d1。元教训：门禁的严格度必须等于契约本身。
Discipline · 目录布局与证据纪律
  • 三代防撞：episode 目录 = session/gen-NNN/attempt-N/{run_id}-{slug}-{sample_token}。trainer 会多次调用 generate_sequences（校验 + 每 step），只有 sample_token 会改写上一轮目录；episode writer 对已存在根 fail-closed。
  • 工作区两坑：放 episode 根之下 → parents=True 预建根，全批死在 mkdir(exist_ok=False)；放 attempt 目录旁 → 批门禁把每个子目录当 episode 读出「缺证据」。所以工作区住兄弟树。
  • dispatch-trace.jsonl：每 episode 派发一行（pid、attempt、sample_token、output_dir 是否已存在），O_APPEND 防并发覆写，诊断失败绝不打断 rollout——「重复派发」与「盖错章」从此可分辨。

把 tuple≠list 这个 bug 完整讲一遍：现象、为什么难定位、两个修复、元教训。
先答：deep-freeze 导致存证 tuple vs 重建 list，容器比较恒 False → 门禁不可满足；两边持久化 → 无法复现差异；修 = 逐元素比较 + 自解释报错；教训 = 比较语义绑定序列化语义。
注意讲出「不可诊断的失败 → 自解释的失败」这条升级线（describe_sequence_difference 会报 first_diff_index 与容器差异）。
「配置存在但从未生效」的静默失败，怎么发现、怎么防御？
先答：except 里 re-raise 让 max_attempts 变单发；发现靠 smoke26 的运行结果与预期矛盾；防御 = 重试策略抽成无 GPU 依赖的纯函数 + 白名单 + 拒绝落盘。
关键句：静默失败不抛栈不崩溃，只有第 2 个 attempt 才会到来的路径从未被执行——要让这类决策在单测里被逼出来。

Deep-dive Q&A ×16
A · 设计动机
verl 自带 tool_agent_loop，为什么要自己写一个 AgentLoop？
先答：框架 loop 给不了证据平面——逐调用原生 ids/logprobs、身份绑定、episode 内 verifier 与认证序列；换的是 loop 的「策略」不是「机器」。
  • 训练要的是「策略在某确定权重下逐 token 的真实生成」，Pi 只能经我们的代理访问引擎。
  • mask 语义（生成 vs 观察）是我们的，框架信任它——利用 postprocess 不重 tokenize。
  • 边界：训练循环/advantage/优化器/同步/引擎一行不替代。
证据：四个扩展点（Step 1）；pi_loop.py:1-22。
认证为什么放在 manager 层而不是逐样本 loop / trainer 侧？
先答：契约是批级的，run 是逐样本的；manager 位置 = 生成后、训练前，失败不能旁路。
  • trainer 侧太晚：批已进管线，拒绝要改 trainer 代码。
  • manager 只做三件事：注入策略、认证整批、留 lineage。
证据：verl_manager.py:12-25。
零方差批为什么重画而不是跳过/给默认 advantage？
先答：advantage 恒 0 是纯噪声；造信号违反 fail-closed；重画因为什么都没被消耗且是抽签性质。
证据：resampling.py:1-15；1/16 实测；r3 max_attempts=20。
为什么要「prompt 即账本」的 append-only 设计？
先答：让 prompt_{i+1}=prompt_i+gen_i+obs_i 由构造成立，避免重 tokenize 改写历史；严格契约无需松弛。
证据：token_context.py:1-11、:112-157。
B · 技术选型与对比
rollout 为什么走 token 级 RPC 而不是 chat API？
先答：要每轮原生 token ids + logprobs（行为策略证据唯一来源），并绕开 decode/re-encode 漂移。
  • 代价：自己接管 stop/预算/拼上下文/工具解析/特殊 token 处理。
  • 采样参数进身份：sampling_fingerprint = sha256({temperature, top_p})。
证据：native_transport.py:188-208；Pearson 0.99957/0.99959。
工具调用解析为什么不能只信 vLLM parser？「不修复」是什么？
先答：smoke16 实测 10/10 解析出 0 个调用；解析只做提取绝不修复，坏输出交给奖励与批门禁裁决。
证据：native_transport.py:16-50；parser 抛异常也回落严格提取器（未提交 diff）。
清洗失败在框架路径是 raise（fatal），旧路径是 report——为什么接受这种不对称？
先答：语义没变（都 fail-closed），变的是表达方式：raise 是框架 API 内让整批停在训练器之外的唯一机制，再配白名单重采样接住可重试失败。
证据：旧路径 1/4 解出率是运气（真实 ~1/16）；smoke24/25/26。
「只有一行数据」和「每步赌解出」是一回事吗？
先答：不是——前者是多样性问题（加行即解，行数=步数）；后者是单批可认证性问题（1000 行也救不了，每行都要独立过闸）。同一个根：任务难度与策略能力错配。
证据：APPS 0/80 全灭 vs Mbpp/118 ~1/16。
C · 踩坑与优化
讲「门禁永远不可能通过」的 bug（tuple ≠ list）。
先答：deep-freeze tuple vs 重建 list，容器比较恒 False；修 = 逐元素比较 + 自解释报错；教训 = 比较语义绑定序列化语义。
证据：sequence.py:98-164；commit 6ec0ad5。
讲「配置存在但从未生效」的 bug（单发重试）。
先答：except 里 re-raise 让 max_attempts 单发；修 = 独立纯函数 + 白名单 + 拒绝落盘；原则 = 让值得测的决策住在值得测的地方。
证据：resampling.py:8-15；commit bc06a5f。
无工具调用回合为什么从 raise 改成合法样本？
先答：它仍是样本（有动作/结局/reward）；raise 把弱样本放大成全批损失（smoke23 连带扔掉兄弟样本）；裁决权归还批门禁。
证据：pi_loop.py:279-290；commit 33347d1。
episode 目录命名为什么是三代防撞？工作区为什么住外面？
先答：session/gen-NNN/attempt-N/sample_token 四维防改写与防撞（trainer 多次调用、重采样重画）；工作区住兄弟树（预建根团灭 + 被当 episode 两坑）；dispatch-trace 留派发证据。
证据：pi_loop.py:87-106、:122-150。
D · 异常与边界
verifier 崩了为什么不能给 reward=0？
先答：0 是训练信号，基础设施失败不是；只认 PASSED/FAILED 终止性判定，其余 raise。
证据：pi_loop.py:293-304；verl_manager.py:289-294。
截断、中止、完成怎么区分？吃满预算的回合是错误吗？
先答：解码层三态（EOS/停止条件/预算打满）；截断合法——verl 自己从不查 EOS；中止才 raise。
证据：tool_agent_loop.py:246/:254；smoke22 3584 全饱和。
引擎无法自报步数，身份怎么钉？
先答：框架写出的 checkpoint 目录树摘要进 adapter_revision + 指纹三层绑定；缺口如实落盘（engine-notes、unconfirmed_steps）。
证据：verl_manager.py:165-184；smoke27 gen-001 digest == P1。
清洗都过了，为什么还要校验框架返回的批？
先答：认证对象是落盘证据，训练器消费的是框架拼的 tensor——L4 校验「框架没动过认证过的任何东西」（数量/uid 组/token/mask/padding/logprobs/reward）。
证据：verl_manager.py:351-384。哲学：三次亮相逐位一致，对不上宁可这步不训练。
Never Say · 绝对不能说的四句话
01

「训练有效 / 涨点了」holdout 33.33% vs P0 29.17% / P12 31.25%，Fisher p=0.826/1.000，n=48 不显著；2/32、1/32 是噪声。只能说「实验已按此功率设计」。

02

「这是一套完整的训练系统」五条件不满足：数据供给 ❌ / 跨 run 接线未实测 ⚠️ / 可移植 ⚠️ / 可评价 ❌ / 自愈 ⚠️。

03

「任何任务都能训」APPS 0/80 全灭；只有解出率落在中间带的数据可用——数据供给问题，不是接入问题。

04

「verl 的 reward / advantage 是我们的」正好相反——reward manager 被绕过（如实说），advantage/优化器/同步全归框架。

回到准确表述 · The Accurate Claim
机制上完整跑通并有实测证据；作为日常可用的训练系统还不行——差的不是集成，是数据供给、跨 run 可续性和可评价性。
