# V2.1 进展：深层 Trace 与 bounded Recovery Policy（已归档）

> 状态：replay 与 policy 基础设施已完成；runtime Hook 接入和效率 Gate 仍在进行。

## 本阶段回答的问题

V2 已经可以观察工具外部行为，但黑盒 Pi 不暴露 Harness 内部 decision。V2.1 开始增加：

```text
structured TOOL_RESULT
→ bounded recovery policy
→ derived replay plan
→ optional HarnessHook decision fact
```

本阶段不修改 V1/V2 的 canonical `TraceEvent` / `AgentEpisode` 语义，也不修改 `configs/gates/reference-v2.json`。

## 已完成

### 1. Structured tool error normalization

Pi adapter 只对明确的 `tool_execution_end` error result 规范化 `ENOENT`：

```text
error_code = FILE_NOT_FOUND
error_path = /...
error_source = pi_tool_protocol
```

原始 `result` 仍然保留在 `TOOL_RESULT.attributes.result` 中。模型文本不会被当成结构化文件错误。

### 2. Decision-aware HarnessHook

`HarnessHook` 支持为 decision fact 附带：

- trigger event IDs；
- policy name/version；
- scope key；
- budget before/after；
- cache hit；
- decision-specific details。

支持的事件包括：

```text
HARNESS_DECISION
RETRY_SCHEDULED
TERMINATION_DECIDED
CONTEXT_SELECTED
CONTEXT_COMPACTED
```

没有 Hook 时，相关 capability 仍然是 `NOT_OBSERVABLE`。

### 3. Bounded FILE_NOT_FOUND policy

当前实现是无隐式全局状态的纯 decision function：

```text
RecoveryInput snapshot
        ↓
RecoveryDecision
```

规则：

```text
非 FILE_NOT_FOUND       → NO_ACTION
缺少 error_path          → TERMINATE
无 cache 且 budget=0     → TERMINATE
无 cache 且 budget>0     → DISCOVER，并消耗一次预算
唯一缓存候选             → READ
零候选                   → TERMINATE
多候选                   → TERMINATE
```

多候选默认终止而不是猜测文件，以避免读错文件后产生看似成功的错误答案。

### 4. Episode-scoped RecoveryController

`RecoveryController` 负责把纯 policy 接入一个 Episode 的 Harness 生命周期：

```text
TOOL_RESULT
  → handle_tool_result()
  → RecoveryDecision
  → optional HarnessHook
  → actual Harness action
```

controller 自己维护当前 Episode 的 discovery cache、attempted scopes 和剩余 budget；不同 Episode 不共享这些状态。discovery decision 一旦产生，scope 立即标记为 attempted，即使工具结果尚未返回，也不会再次发起同 scope 搜索。

controller 不执行 `find` 或 `read`，也不修改 `TraceEvent`；它只返回 action 并可选记录 decision fact。

`RecoveryExecutionAdapter` 负责把 action 交给一个 `RecoveryToolExecutor`，并限制一次 recovery 最多执行一个 discovery 和一个 read。当前提供的 `LocalRecoveryToolExecutor` 只用于受控本地 workspace fixture：不执行 shell，所有路径必须位于 workspace 内，并为实际工具调用生成 `TOOL_CALL/TOOL_RESULT`。

`ToolDispatchRequest` 是真实 Harness 接入边界：它保留 action、arguments、decision checksum、policy version、trigger event IDs 和 parent span。真实 Harness 只需要实现 `RecoveryToolDispatcher.dispatch()`，不需要重新实现 policy 或 controller。

### 5. Derived replay

新增 `demo-v21`：

```bash
python3 -m src.cli demo-v21 --output artifacts/v2.1-recovery-replay
```

它读取已脱敏的 V2 Pi fixtures，运行 policy replay，并输出：

- `recovery-replay.json`；
- `capture-evidence.json`；
- `summary.json`；
- `artifact-manifest.json`。

replay 不向 raw events 追加 synthetic `HARNESS_DECISION`，因此不会把分析结论伪装成运行时事实。

## 当前 replay 结果

```text
6 个 Episode replayed
candidate policy/action alignment: MATCH
control runtime decision claim: none
raw events modified: false
runtime decision capture: NOT_OBSERVABLE
```

对 candidate fixture，replay 计划为：

```text
FILE_NOT_FOUND
→ DISCOVER
→ unique candidate
→ READ
```

现有 candidate trace 中观察到的 `find` 和 `read` 与该计划一致。但因为 fixtures 本身没有 Hook decision event，只能说：

> observed actions are consistent with the policy replay plan

不能说：

> Harness runtime emitted these decisions

`demo-v21-runtime` 另外生成一个明确标记 `not_real_pi=true` 的本地 runtime evidence package。3 个本地 Episode 都能 `COMPLETE` 组装，每个包含 `DISCOVER → READ` decision 和实际 find/read tool events；它验证的是 controller/executor/Hook 集成，不是 Pi runtime evidence。

## Container smoke boundary

当前增加了最小容器运行目标：

```bash
scripts/container-smoke.sh
```

它构建 `python:3.10-slim` image，运行 `demo-v21-runtime`，并验证 volume 中生成 `summary.json` 和 `episodes.jsonl`。这是 portability smoke test，不是 V2.3 production deployment：不包含 queue、object storage、multi-tenant、online service 或真实 Pi credentials。

## 当前限制

1. V2.1 replay 是 derived evidence，不是真实 Hook capture；
2. 还没有将 bounded policy 接入真实 Pi Harness 的决策执行路径；
3. 还没有重新测量 policy 接入后的 token/latency Gate；
4. 3 对任务仍然只证明 reference mechanism；
5. policy 的多候选终止规则是安全默认值，后续可根据真实任务证据演进。
